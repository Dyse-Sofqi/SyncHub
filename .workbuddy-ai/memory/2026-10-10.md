## 轮次：`.gitignore` 代码框全宽失效 —— CSS 注释被 `*/` 提前结束

用户报：「`.gitignore` 的输入框全宽失效了，应该默认和页面等宽才对」。

### 根因（真 bug，不是预览假象）

`styles.css` 第 1067-1068 行的注释里写着「路径分隔与通配符（`!` 取反、`**/` 递归）」，
而 **`**/` 里含 `*/`** —— CSS 注释在那一行就**提前结束**了。剩下的文字被解析器当成
**下一条规则的选择器**，于是紧接着的

```css
.obsync-settings .obsync-gitignore { width: 100%; box-sizing: border-box; min-height: 12em; … }
```

被**整条静默丢弃**：不报错、不警告。代码框只剩 textarea 的默认宽度 **173px**（容器 660px），
同一段里的 `min-height` / `white-space` / `padding` 也一起失效。

**为什么难查**：`el.matches('.obsync-settings .obsync-gitignore')` 返回 **true**
（DOM 层面选择器没问题），而 `pnpm check` 第 4 项（CSS 类覆盖）照样通过 ——
它用正则扫 `obsync-*` 字符串，**被丢弃的规则在文本上仍然「有定义」**。
判据与「CSS 到底解析出了什么」之间隔着一层，而那层是真的解析器。

### 量它的办法（别靠读 CSS 猜）

项目里有现成的设置页预览探针 `.probe/settings-preview`：

```bash
cd .probe/settings-preview
node build.mjs                       # src 改了才需要
node eval.mjs "file:///F:/_Workspace/SyncHub/.probe/settings-preview/page.html?page=sync" "<表达式>"
```

它把**真实的 `src/settingsTab.ts` + 真实的 `styles.css` + 真实 app.css/theme.css**
放进 headless Chromium。取 `getBoundingClientRect().width` 与
`getComputedStyle().minHeight` 就能一眼看出「规则有没有生效」。

> 两个踩到的坑：
> 1. **`document.styleSheets[..].cssRules` 在 file:// 下抛 `SecurityError`**（同源策略）——
>    我第一版的 try/catch 把它整个跳过，于是 `foundRules` 恒为 `[]`，得出「规则没被解析」
>    的**假阴性**结论。要读 cssRules 得给 Chrome 加 `--allow-file-access-from-files`，
>    或者干脆别用这个判据。
> 2. `display: block`、`box-sizing: border-box` 这类**不能当证据** ——
>    app.css 全局就有，看着像「我们的规则生效了」。

### 修法与防线

- 改掉那句注释的措辞（不再出现 `*/`）；
- `scripts/checks.mjs` 新增**第 8 项「CSS 注释完整性」**：模拟解析器 ——
  注释在第一个终止符处结束，此后遇到的终止符即游离（= 它前面那条规则被吃掉了）。
  拿修复前的 `styles.css` 验过：**检出 1 处（第 1070 行）**，修复后 0 处。
- **写这道检查时我自己又踩了同一个坑**：在 `checks.mjs` 的注释里直接写了那个两字符
  组合，于是**这个 JS 文件**报 `SyntaxError: Invalid regular expression: missing /`。
  同一个坑、同一天、第二次 —— 注释里的 `**` 后面**永远不要紧跟斜杠**。

### 验证与部署

`pnpm check` **八项全过**（新项报 0 处）、`typecheck`、`lint:review` 全绿；
`pnpm build:both` 部署两库。修复前后实测：代码框宽度 **173px → 660px**，
`min-height` 0 → 144px，`white-space` pre-wrap → pre。

### 最重要的一条结论（重新框定了清理的代价）

**重写的代价只吃「提交总数」，与每个提交改了什么、改了多少字节无关。** 于是：

- 20 MB 但有 10000 个「只改一行」的提交 → 重写约 10 小时；
- 500 MB 但只有 200 个提交 → 重写约 12 分钟。

所以**真正要防的不是大文件，是「无意义的提交把提交数推高」**。大文件拦截防的是**体积**，
防不了这个 —— 两件事是两条独立的轴。

## 轮次：用户问「定时同步该不该拆成短间隔暂存 + 长间隔同步」与「暂存能否恢复」

### 查清的事实（都实测过）

1. **`sync()` = commit → pull → push**（`syncService.sync`）。定时同步调的就是它。
2. **插件没有任何「恢复」动作**。全部动作：提交 / 取消暂存 / 拉取 / 推送 / 同步 / 刷新 /
   查看差异 / 在远端打开 / 停止跟踪 / 放弃合并。没有「放弃更改」「从索引恢复工作区」。
   - 「取消暂存」是 `git restore --staged`（索引退回 HEAD），**工作区一个字节不动** ——
     它丢掉的恰好是「暂存的那份」。
   - 真要恢复得用 `git restore --worktree`（索引→工作区）或
     `git restore --source=HEAD --worktree`（HEAD→工作区），**两个都没暴露**。
3. **暂存的内容扛得住 gc**（合成仓实测）：`git add` 写下的 blob 在
   `git gc --prune=now` 之后**还在**，连 `reflog expire --expire=now --all` + 再 gc 之后
   **也还在**（索引是 git 的可达根之一）。所以「暂存」比工作区安全，但**不如提交**：
   不在历史、不在云端、其他设备看不到，而且一个 `git reset` 或索引损坏就丢掉引用
   → 对象变不可达 → 下次 gc 收走。
4. `intervalMinutes` 默认 10，可设 1..1440。

### 对「拆成短间隔暂存 + 长间隔同步」的判断（未实现，等用户定）

**思路对，但「暂存」是错的机制**，三条理由：

1. **与 pull 冲突（实测两档）**：
   - `pull --rebase`：**一定**被拒 —— `error: cannot pull with rebase: Your index contains
     uncommitted changes. / Please commit or stash them.`
   - `pull`（merge）：改的是**不同文件**时能过（实测 fast-forward 成功）；
     **两边改了同一个文件**时被拒 —— `error: Your local changes to the following files
     would be overwritten by merge: a.md`。
   所以长间隔那一步**在 rebase 策略下必须**先 `commitAll`；merge 策略下多数时候能拖，
   但恰恰在「两边撞上同一个文件」这个最需要它停下的时刻会被拒。方案**没省掉提交，只是推迟**。
2. **风险窗口变长**：现在最多丢 10 分钟的工作，拆完变成 30 分钟。
3. **用户的数据不支持现在就做**：161 提交 / 约 20 个月 ≈ **每月 8 个**，定时器根本没在
   制造提交；而且刚修完的「本地状态文件」已经把最容易制造噪音的那类堵掉了。

### 更好的替代（若真要减提交数）

**合并到上一个尚未推送的提交（amend）**：保持 5 分钟频率，把本次改动并进上一个
**未推送**的同步提交。安全性不降（内容照样进历史），提交数由**推送间隔**决定而不是
定时器间隔。规则要写死：只合并**本插件自动生成的、且 `ahead > 0` 的**那个提交
（别人推过就 `ahead` 归零，自然退化成新提交）。

### 用户的决定：**先不动**

保持现在的定时同步。理由就是上面第 3 条 —— 实际提交率每月 8 个，定时器没在制造提交；
先把「本地状态文件」那一修的效果看一轮再决定。**别在下一轮主动重提这两个方案**，
除非用户先说起，或者出现了新的数据（比如提交数真的开始涨）。

留档的两个未做项（等用户开口）：
- **amend 合并**（上面那段的设计已经完整，可直接照着实现）；
- **「恢复」动作缺口**：插件没有任何「丢弃工作区改动 / 从索引恢复」的动作，
  真要补得单独设计（它是真正的数据丢失动作，要带确认）。

## 轮次：三层保护的分工 —— 实现「检测并提示」+ 定下同步频率

用户要「不脏 git 记录 + 高频防丢失 + 能从旧版本恢复」的方案，然后让我做「检测并提示」，
并问推荐的同步频率。

### 核心结论（这套推理是这一轮最有价值的东西）

**这三件事不冲突，之前觉得冲突是因为把「高频保护」交给 git 了。** git 的恢复粒度是
**全库提交**，而高频恢复要的是**单文件回滚** —— 用提交去满足它，提交数就等于编辑次数。
git 不可替代的价值是**长期 + 跨设备 + 不可变**，那恰恰是**低频**需求。

三层分工：

| 需求 | 粒度 | 谁承担 | 进 git 吗 |
| --- | --- | --- | --- |
| 高频防丢失 | 分钟级、单文件、带 diff | Obsidian「文件恢复」 | **完全不进**（IndexedDB） |
| 云端持久 / 跨设备 | 全库快照 | SyncHub 定时同步 | 进 |
| 从旧版本恢复（>7 天） | 长期、不可变 | git 历史 | 进 |

### 「文件恢复」的实测参数（从 `.probe/app-extract.js` 抠的）

`options = Object.assign({}, {intervalMinutes: 5, keepDays: 7}, await loadData())`；
触发是 `vault.on("modify")` + `workspace.on("file-open")` + 每 60 秒 `resave`；
`defaultOn = true`；存 IndexedDB 的 `backups` 表（按 `path` 索引，带 `ts`）；自带 diff 视图。

**用户两个库里 `file-recovery` 都是 `false`** —— 而且 `sync.enabled` 也都是 `false`。
所以真实风险不是「提交太多」，而是**两层都没兜住**。

### 实现的（很小）

`corePluginState.ts` 的 `corePluginEnabled(json, id)`（纯函数）+ `syncService.fileRecoveryEnabled()`
（只读 `${configDir}/core-plugins.json`）+ `renderSync` 里「注意事项」的**第三条**，
**只在它关着时出现**。设置页预览验过：默认 2 条，`?filerecovery=0` 时 3 条。

三条设计约束：读文件而不是 `app.internalPlugins`（非公开 API）；只读不写（改别人的
核心插件要重启才生效）；**读不出来（`undefined`）时什么都不加** —— 不猜。

### 频率：推荐 30 分钟，并把默认值从 10 改成 30

理由：高频已交给文件恢复 → 定时同步只剩「云端新鲜度 + 跨设备」，而灾难恢复本身要花几小时，
丢 30 分钟与丢 5 分钟没实际差别；跨设备有「立即同步」兜底。间隔越短提交数越线性增长。

**踩到一条测试**：`settings.test.ts` 里那条「不污染 DEFAULT_SETTINGS」的用例把默认值
**写死成 10**（两处）。已改成先捕获 `originalInterval` 再比 —— 断言的是「有没有被污染」，
不该因为「调默认值」而红。**改默认值前先 grep 测试里的硬编码数字。**

### 自我修正：amend 的价值比我上一轮说的小

它当初是作为「短间隔暂存」的替代提的，那条比较仍成立；但 SyncHub 的同步是
commit + push 一体，amend 要有意义得把两者拆开，而拆开之后它提供的「本机高频 git 快照」
和文件恢复高度重叠（后者还更细）。**不是错的，是没必要的。**

## 轮次：去掉面板上的逐文件暂存（发 0.2.2 前）

用户问「你刚才提到暂存会影响拉取，那是不是不应该暂存？」

### 先更正我自己的表述（实测两档，都不准）

| 情况 | `pull --rebase` |
| --- | --- |
| 索引里有暂存 | `cannot pull with rebase: Your index contains uncommitted changes.` |
| **只有工作区改动** | `cannot pull with rebase: You have unstaged changes.` |

**两者都被拒** —— rebase 要的是「索引与工作区都干净」，**不是暂存特有的问题**。
而且 `sync()` 是 commit → pull → push，拉取在提交之后，**正常链路碰不到**。

### 真正的问题（读 `doCommitAll` 才看出来）

`doCommitAll` **无条件 `git add -A`** → **手动暂存了什么对最终提交毫无影响**；
更要紧的是**定时同步到点会把它们一起提交掉** —— 那个按钮**连「暂时不提交」都做不到**。
用户暂存 A 想只提交 A，结果 B 一起进去了。

### 决定：四个按钮 + 两个服务方法一起删（用户选的）

- 删：面板的「暂存此文件 / 取消暂存」+「全部暂存 / 全部取消暂存」、
  `SyncService.stageFiles` / `unstageFiles`、四个 i18n 键。
- **保留**：按暂存状态的**分组**（冲突文件在 `git status` 里同时进 staged 与 unstaged，
  去重后落在「已暂存」那组，所以那组不是空的）；git 层的 `GitManager.stage` / `unstage`
  —— 抽象层词汇，`stage` 还被 `doCommitAll` 用，且 `unstage` 的 `HEAD_UNBORN_RE`
  分支守着「HEAD 未出生时 `git restore --staged` 报 `fatal: could not resolve 'HEAD'`
  （**带单引号**）」这条坑，有集成测试钉着。
- 依据是本仓库已有的同类判断：嵌套仓库行里那个 `minus`（暂存不下）被去掉时的理由 ——
  「**点了没反应的按钮，留着只会让人以为插件坏了**」。暂存按钮更糟：**有反应但没效果**。

**SyncHub 不做选择性提交。** 真要让暂存生效，得同时改「提交」与**自动同步**的行为，
否则自动同步会把这份选择抹掉（那正是这个项目最恨的「以为发生了但没发生」）。

## 轮次：修「立即同步」报 `NoUpstreamError`（用户报的 bug）

用户原话：在 learning-records 仓库点「立即同步」报

```
[SyncHub] operation failed En: pull: current branch has no tracking remote branch
```

### 死锁的根

`sync()` 的顺序是**提交 → 拉取 → 推送**，而 `pull()` 里

```ts
if (!status.current || !status.tracking) throw new NoUpstreamError(...)
```

硬要求分支已配置上游。**可建立上游的恰恰是推送**（`push()` 用 `git push -u origin <branch>`）——
于是拉取先报错、推送永远轮不到、上游永远建不起来。**第一次同步必然卡死。**

### 用户仓库的真实状态（`D:/_Workspace/learning-records`）

- 分支 `master`，`origin` = `https://gitee.com/sofqi/learning-records.git`（另有一个同 URL 的
  远端叫 `学习记录`）。
- `git branch -vv` 显示 `master` **没有** `[origin/master]` —— `branch.master.remote/merge` 没写。
- **但 `refs/remotes/origin/master` 是存在的**（`b22a2ab`），本地领先 2、落后 0。
  也就是说「远端分支在、只是没配上游」—— 正是最容易被误判成「仓库没配好」的形态。

### 修法（`SimpleGitManager.pull`）

1. `!status.current` → `DetachedHeadError`（不再是 `NoUpstreamError` —— 游离 HEAD 与
   「没上游」应对方式不同，混用会把用户指错方向）。
2. 没有远端（`getRemoteUrl()` 为空）→ `NoUpstreamError("no remote configured")`。
   与 `testRemoteAccess` 同一判断。**注意**：`NoUpstreamError` 的语义收窄了 ——
   现在专指「连远端都没配」，所以 `t.sync.noUpstream` 的文案也改成
   「还没有配置远端仓库，无法拉取。请在设置中填写远端地址。」
3. **fetch 之后**再定上游：`status.tracking ?? (refExists("origin/<branch>") ? "origin/<branch>" : undefined)`。
   顺序要紧 —— 从没 fetch 过的仓库看不到远端分支。新增私有 `refExists()`
   （`rev-parse --verify --quiet`，不存在返回 false 不抛）。
4. 上游仍然没有（远端连这个分支都没有）→ 返回 `up-to-date`，**不报错** ——
   让链路走到推送，由 `-u` 把上游建起来。

顺带把 `t.sync.detachedHead` 的文案从「无法推送」改成「无法同步」（现在 pull 也会抛它）。

### 验证

- 新增 2 条真仓库测试：① 抹掉上游配置后 pull 仍能带回远端提交；② 远端还没有该分支时
  pull 返回 up-to-date，随后的 push 建起上游。
- `pnpm check` 八项全过、`pnpm test` **93 文件 1984 用例全绿**（比上轮多 2 条）、
  `build:both` 部署两库，三个产物 SHA256 与源码一致。
- **顺手修了用户的库**：`git branch --set-upstream-to=origin/master master`
  （本地、可逆、就是推送本来会做的事）—— 这样即使不重载插件，`master` 也立刻有上游。

**这不是新 bug，是重写历史的固有后果**（插件文档里就写着「必须强制推送」）。
真正的缺陷是**插件没给这个状态留出口**：那个强制推送只存在于清理弹窗的
**结果页**上，用户关掉窗口、重启 Obsidian 之后就再也找不到了 ——
而他点「立即同步」拿到的是一句**英文 git 原文**，没有任何可行动信息。

### 改了什么（两件事，缺一不可）

1. **错误有了类型与文案**：新增 `UnrelatedHistoriesError`；`mapError` 认
   `refusing to merge unrelated histories`；`describeSyncError` →
   `t.sync.unrelatedHistories`（说清「重写之后还没强制推送」+ **指出强制推送在哪**）。
   放在推送判断**之前**，且**绝不能**落进 `PushRejectedError`（那句说的是「先拉取」，
   而在这个状态下拉取同样走不通，用户照做只会原地打转）。
2. **强制推送有了持久入口**：设置页「清理」一节新增一行「强制推送（重写历史之后）」，
   与「丢弃备份」一样由 `listBackups()` 决定可用性 —— **备份引用写在 git 里**，
   所以这个信号跨重启、跨设备都在（不是弹窗实例上的内存状态）。
   走 `service.forcePush()`，与结果页那颗按钮同一份实现。
   顺序是「强制推送 → 丢弃备份」（先推、确认没问题再扔退路），所以新行排在它前面。

顺带：`pull()` 在动手**之前**先查 `merge-base`，没有共同祖先就直接抛 ——
因为 merge 被拒是无害的，但 **rebase 会真的开始重放**，留下一仓库冲突。

### 一个必须记住的 simple-git 坑（这次踩到的）

**`git.raw(["merge-base", a, b])` 在「没有共同祖先」时 resolve 出空串，不抛。**
`merge-base` 是以 exit 1 退出**且什么都不输出**（连 stderr 都没有），
而 simple-git 对「非零退出 + 两边都没内容」**照样 resolve**。实测（脚本留在
`.probe/mergebase-check.mjs`）：

```
HEAD = f47085d…  origin/master = 1a2a11b…
merge-base RESOLVED, output = ""
```

第一版写成「抛错就算没有共同祖先」→ **永远返回 true**，那条保护形同虚设
（rebase 照跑，而测试里它真的 resolve 成了 `{kind:"pulled"}`）。
判据必须读**输出为空**，与 `refExists` 的 `sha.trim().length > 0` 同一个写法。

### 测试

- `simpleGitManager.test.ts` 真仓库 1 条：手工造「本地孤儿历史 vs 远端旧历史」，
  钉住 merge/rebase **两条路径都在动手前被拦**，且工作区一个字没动、
  没有 `rebase-merge` / `rebase-apply` 残留。
- `gitErrorMapping.test.ts`（映射）与 `syncErrors.test.ts`（文案，
  并钉「不能退化成推送被拒那句」）。
- `settingsTabRender.test.ts` 3 条：没有备份时置灰、有备份时可用且排在
  「丢弃备份」之前、点它走 `service.forcePush()`。

### 用户的库怎么收拾

Plugin-Test 停在「本地已重写、远端还是旧历史」。出路就是**一次强制推送**
（新加的那一行，或 `git push --force -u origin master`）。
**没有替用户执行** —— 那是改远端历史的对外动作，得他自己点。

## 轮次：第二次重写失败 + **重写会删掉用户的本地文件**（两个真 bug）

用户原话：

> 重写报错了，弹框提示没适配中文，控制台报错：
> `plugin:ob-sync:6 [SyncHub] operation failed ht: Cannot create a new backup.
>  A previous backup already exists in refs/original/ Force overwriting the backup with -f`

### 现场（Plugin-Test）

| 事实 | 值 |
| --- | --- |
| 本地 HEAD | `6cbb06c`（27 提交），`origin/master` 也是它 —— **上次的强制推送成功了** |
| 备份引用 | `…-114300`→`2d02877`（第一次重写前）、`…-122044`→`6cbb06c`（12:20 那次尝试建的） |
| `refs/original/*` | → `2d02877`（**11:43 那次重写留下的**） |

### Bug 1：第二次深度清理**必然失败**

`filter-branch` 把「改写前的引用」备份在 `refs/original/`，见到它已存在就**拒绝开始**。
而插件只在「丢弃备份并回收」里清它 —— 也就是**清理两次之间必须先丢弃备份**，
而 `cleanup.ts` 里备份引用带时间戳的理由恰恰是「用户可能清理多次」。实现与设计意图不符。

**修法**：`filter-branch` 加 `--force`（git 直接覆盖那份中间引用）。
**为什么安全**：`refs/original` 是 filter-branch 自己的记账，我们的退路是
`refs/obsync-backup/<时间戳>` —— 那个命名空间不在 `--branches --tags --remotes` 里，
一次都不会被改写。合成仓实测：连续两次重写，两份备份各自仍指向它那次重写前的提交。
（`.probe/fbtest*` 的合成仓实验：不加 `-f` → exit 1 + 那段英文；加 `-f` → exit 0，
`keep/` 被剔除、`stay/` 保留、两份备份都在。）

### Bug 2（更重）：**重写会把剔除的路径从磁盘上删掉**

`git filter-branch` 的**最后一步**是 `git read-tree -u -m HEAD`（读脚本末尾确认的：
`if [ "$(is_bare_repository)" = false ]; then git read-tree -u -m HEAD || exit; fi`），
作用是把工作区对齐到改写后的 HEAD —— **被剔除的路径因此从磁盘上消失**。

用本类真实的 `rewriteHistory` 实测（`.probe` 里的临时用例）：
`drop/b.md 还在磁盘上？ false`，`keep/a.md 还在磁盘上？ true`。

而界面与文档都写着「只清历史，本地文件一个都不动」（`syncService.rewriteHistory`
的注释原文如此）。**勾一个装着笔记的目录，笔记就没了** —— 这个动作的目的是
「让 git 以后别跟踪它们」，不是「删掉它们」。

**修法**：filter-branch 之后用 `git restore --source=<备份引用> --worktree -- <路径>`
把路径放回磁盘。两个细节：**必须用 `git restore --worktree`**（`git checkout <ref> -- <path>`
会把文件**加进索引**，实测 `status` 显示 `A  drop/b.md`，等于又跟踪起来）；
**逐个路径**恢复（某个路径在重写前的提交里不存在时整条命令会失败，
一次全传会让能恢复的也一起不恢复）。确认页也补了一句「本地文件都会留着」——
那是承诺，不是安慰。

### Bug 3（顺带坐实）：`filter-branch` 报错 ≠ 什么都没发生

引用是**边改写边 `update-ref`** 的，而收尾那次工作区同步在**之后**才跑 ——
它失败会让命令以非零退出，但历史**已经变了**。拿退出码当结论就会把
「历史已改写、只是工作区没同步」报成「重写失败」，于是忽略规则不写
（下次同步把刚剔掉的路径原样提交回去）、结果页不出现（用户不知道要强制推送），
而真正的后果（哈希全变、远端分叉）已经发生了。**报错与后果对不上。**

这大概率就是用户 11:43 那次的经过：他库里 `a80fda7`（12:02 那次提交）里
**206 个文件**又回来了，`.gitignore` 里也没有 `stock/` 之类的规则 ——
两条都说明「忽略规则当时没写」，也就是那次重写被报成了失败。

**修法**：改由「引用动没动」回答（`head === previousHead` 才算真失败），
`failure` 只在引用没动时抛出，否则记一条 `logger.warn` 继续走完
（写忽略规则 + 返回结果）。取舍写在注释里。

### Bug 4（顺带发现）：`--prune-empty` 可能把分支整个删掉

勾选的路径覆盖了每个提交的全部内容时，没有提交能活下来，
filter-branch 会把分支**整个删掉**（实测原话 `Ref 'refs/heads/master' was deleted`），
仓库落到「HEAD 未出生」。**修法**：检测到就 `update-ref refs/heads/<branch> <重写前 HEAD>`
接回去，再抛 `HistoryRewriteEmptiedError`（文案重点是「已经还原了，库是好的」）。

### 新错误类型与文案（用户那句「没适配中文」）

`HistoryRewriteRefusedError`（refs/original）与 `HistoryRewriteEmptiedError`，
`mapError` 认 `A previous backup already exists in refs/original`，
`describeSyncError` 出中文。这是本项目一贯的规矩：**绝不让 git 的英文原文
落在用户面前** —— 它不含任何可行动信息。

### 测试（新增 3 条真仓库用例，这一层此前一条都没有）

`describe("深度清理（重写历史）")`：连续两次重写都能跑通 + 两份备份各自指向它那次
重写前的提交；**被剔除的路径还在磁盘上**且不在索引里；整条历史被清空时分支被还原。

> ⚠ 这组**很慢**：本机 `filter-branch` 一次约 **28 秒**（它内部起几十个子进程，
> 而本机进程创建约 340ms），所以三条都带**显式超时**（90s / 120s）。
> 别把默认 30 秒当成「它卡死了」。

### 用户现在的库是什么状态

第一次清理是**半成品**：历史确实改写了，但忽略规则没写成，
下一次同步把 206 个文件原样提交回去（`a80fda7`），于是那些文件又回到了历史里 ——
空间并没有真正释放。他需要：升级插件后**再清一次**（这次会成功，且文件不会丢），
然后强制推送。







## 轮次：清理的「小白流程」—— 四步收进一个窗口 + 一个持久入口

用户问：「清理的正确流程是怎么操作的？插件有标准流程走完整个清理吗？我需要小白也能操作的方案」

### 先答问题：正确流程是四步，而插件原来只覆盖前两步

1. **体检**（看清空间被什么占了，按目录汇总）
2. **重写**（勾目录 → 确认 → 跑几分钟）
3. **强制推送**（重写之后本地与远端必然分叉）
4. **确认库没问题 → 丢弃备份**（空间到**这一步**才真正释放）

第 3 步原来只在弹窗结果页上，第 4 步在设置页的另一行，中间还要用户自己判断
「库是不是没问题了」。而结果页的次要按钮写着「完成」—— 于是「做完重写就走了、
空间没释放」是**必然**的结局，用户会得出「这个清理没用」。

### 改了什么

- **结果页的主操作变成「强制推送」**，推完**自动切到收尾页**；次要按钮从「完成」
  改成「稍后再说」（`result.done` 这个键删掉了 —— 它是在骗人）。新增
  `result.nextSteps` 把「还剩最后一步」明说出来。
- **新增收尾页 `settle`**：① 强制推送（推过就打勾、且**不再给**那颗按钮）
  ② **三件可执行的检查**（打开几篇笔记 / 看图能不能显示 / 别的设备重新 clone）
  +「丢弃备份并回收」+「稍后再说」。做完 → `settled` 页说「释放了 X」。
  - 检查清单写具体是刻意的：「确认库一切正常」对用户等于没说。这一步也**不能自动化** ——
    要判断的是「笔记内容有没有被清坏」，只有人看得出来。
- **设置页最上面新增「继续上次的清理」**：可用性由 `refs/obsync-backup/*` 决定
  （写在 git 里 → 跨重启跨设备都在），点它**直接开到收尾页**
  （新增构造参数 `startAt: "settle"`，**不读历史** —— 那要几秒）。
- **「强制推送」那一行不再灰掉**：它可能在「备份已丢弃、但远端还没推」时仍然需要，
  灰掉等于把用户堵死。这是权衡过的取舍（宁可多一行可点的按钮）。
- 「体检仓库历史」→「体检并清理历史」（这一行做的确实是整件事的第一步）。

### 测试

- `cleanupModal.test.ts` 新增一条走完整条链：重写 → 强制推送 → 收尾页
  （已推过、不再给推送按钮）→ 丢弃备份 → 完成页「备份已丢弃」。
- `settingsTabRender.test.ts` 那一组改成「收尾入口」：没有备份时置灰并说明、
  有备份时可用且排在「体检并清理」之前、点「继续」直接开到收尾页、
  「强制推送」不置灰、点了走 `service.forcePush()`。

> 取数手法记一笔：`lastButton(text)` 是从后往前找文案，会命中**上一屏**留下的同名
> 按钮 —— 「推过之后不再给强制推送」这种断言必须只看**当前那一屏**的按钮行
> （`createdSettings.at(-1).buttons`：`addButtons` 每次渲染都新建一个 Setting）。

## 轮次：用户问「清理完 .gitignore 多出目录，同步之后这些目录岂不是不进同步了？」

### 答案：对，而且这是故意的 —— 但界面此前一个字都没说过

- 清历史之后**必须**写忽略规则，否则下一次 `git add -A` 会把它们原样加回来
  （用户库里 12:02 那次 206 个文件回来就是这么发生的），清理白做。
- 所以 **`.gitignore` 必须同步** —— 不同步的话，换设备 clone 之后那份 `.gitignore`
  里没有这些规则，一旦把目录拷过去 git 又会收进来，清理白做。
- 代价就是：**这些目录以后不再跟着 git 同步**。所以「勾哪些目录」＝
  「决定哪些东西不再由 git 管」。

按类别看：插件目录（换设备要重装，插件有「已跟踪」页能一键装回来）、
图片（交给图片同步 / R2）、字体（每台机器装一次）—— 本来都不该走 git。
**笔记目录绝不能勾**：剔了等于这些笔记以后不再同步，别的设备再也看不到。

### 发现并修掉的真缺口：这个后果**没有任何地方说过**

用户问出来才知道 —— 而最危险的误操作（勾一个装着笔记的目录）毫无提示。
补了三处，都在**动手之前**：

1. **报告页的目录行**：有笔记的目录直接写「· 120 篇笔记」（新增字段
   `HistoryDirectory.notes`）。勾之前就该看见这个数字。
2. **报告页顶部 `selectNote`**：补上「勾中的目录以后不会再跟着 git 同步」。
3. **确认页**（路径清单正下方，`obsync-modal-warning` 样式）：`warningSync`
   （以后不进 git、其他设备 clone 之后不会有它们）与 `warningNotes(count)`
   （⚠ 你勾选的目录里有 N 篇笔记…如果这不是你的本意，请返回取消勾选）。
   `ignored(count)` 也补上了后果。

### `HistoryDirectory.notes` 的两个设计点

- **判据只有 `.md` / `.canvas`**（`isNotePath`）：它们是 Obsidian 里只有本机能创建、
  丢了就没的东西。附件另有图片同步兜着，字体/插件本来每台机器重装 ——
  什么都警告等于什么都没警告。
- **按路径去重**（Set）而不是数对象：`entries` 是每个版本一条，直接数会把
  「改过 20 次的一篇」报成 20 篇。用户想知道的是「有几篇」。

### 没做的（已问用户）

「历史里只留一份、但以后**仍然**跟踪」这个诉求现在做不到 —— 得清完之后手动删掉
`.gitignore` 里那几行再提交。要不要在确认页做成一个开关（默认「不再跟踪」），
等用户定。
