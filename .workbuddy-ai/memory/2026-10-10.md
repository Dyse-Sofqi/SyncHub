## 轮次：`.gitignore` 代码框全宽失效 —— CSS 注释被 `*/` 提前结束

用户报：「`.gitignore` 的输入框全宽失效了，应该默认和页面等宽才对」。

### 根因（真 bug，不是预览假象）

`styles.css` 第 1067-1068 行的注释里写着「路径分隔与通配符（`!` 取反、`**/` 递归）」，
而 **`**/` 里含 `*/`** —— CSS 注释在那一行就**提前结束**了。剩下的文字被解析器当成
**下一条规则的选择器**，于是紧接着的

```css
.obsync-settings .obsync-gitignore { width: 100%; box-sizing: border-box; min-height: 12em; … }
```

被**整条静默丢弃**：不报错、不警告。代码框只剩 textarea 的默认宽度 **173px**（容器 660px），
同一段里的 `min-height` / `white-space` / `padding` 也一起失效。

**为什么难查**：`el.matches('.obsync-settings .obsync-gitignore')` 返回 **true**
（DOM 层面选择器没问题），而 `pnpm check` 第 4 项（CSS 类覆盖）照样通过 ——
它用正则扫 `obsync-*` 字符串，**被丢弃的规则在文本上仍然「有定义」**。
判据与「CSS 到底解析出了什么」之间隔着一层，而那层是真的解析器。

### 量它的办法（别靠读 CSS 猜）

项目里有现成的设置页预览探针 `.probe/settings-preview`：

```bash
cd .probe/settings-preview
node build.mjs                       # src 改了才需要
node eval.mjs "file:///F:/_Workspace/SyncHub/.probe/settings-preview/page.html?page=sync" "<表达式>"
```

它把**真实的 `src/settingsTab.ts` + 真实的 `styles.css` + 真实 app.css/theme.css**
放进 headless Chromium。取 `getBoundingClientRect().width` 与
`getComputedStyle().minHeight` 就能一眼看出「规则有没有生效」。

> 两个踩到的坑：
> 1. **`document.styleSheets[..].cssRules` 在 file:// 下抛 `SecurityError`**（同源策略）——
>    我第一版的 try/catch 把它整个跳过，于是 `foundRules` 恒为 `[]`，得出「规则没被解析」
>    的**假阴性**结论。要读 cssRules 得给 Chrome 加 `--allow-file-access-from-files`，
>    或者干脆别用这个判据。
> 2. `display: block`、`box-sizing: border-box` 这类**不能当证据** ——
>    app.css 全局就有，看着像「我们的规则生效了」。

### 修法与防线

- 改掉那句注释的措辞（不再出现 `*/`）；
- `scripts/checks.mjs` 新增**第 8 项「CSS 注释完整性」**：模拟解析器 ——
  注释在第一个终止符处结束，此后遇到的终止符即游离（= 它前面那条规则被吃掉了）。
  拿修复前的 `styles.css` 验过：**检出 1 处（第 1070 行）**，修复后 0 处。
- **写这道检查时我自己又踩了同一个坑**：在 `checks.mjs` 的注释里直接写了那个两字符
  组合，于是**这个 JS 文件**报 `SyntaxError: Invalid regular expression: missing /`。
  同一个坑、同一天、第二次 —— 注释里的 `**` 后面**永远不要紧跟斜杠**。

### 验证与部署

`pnpm check` **八项全过**（新项报 0 处）、`typecheck`、`lint:review` 全绿；
`pnpm build:both` 部署两库。修复前后实测：代码框宽度 **173px → 660px**，
`min-height` 0 → 144px，`white-space` pre-wrap → pre。

### 最重要的一条结论（重新框定了清理的代价）

**重写的代价只吃「提交总数」，与每个提交改了什么、改了多少字节无关。** 于是：

- 20 MB 但有 10000 个「只改一行」的提交 → 重写约 10 小时；
- 500 MB 但只有 200 个提交 → 重写约 12 分钟。

所以**真正要防的不是大文件，是「无意义的提交把提交数推高」**。大文件拦截防的是**体积**，
防不了这个 —— 两件事是两条独立的轴。

## 轮次：用户问「定时同步该不该拆成短间隔暂存 + 长间隔同步」与「暂存能否恢复」

### 查清的事实（都实测过）

1. **`sync()` = commit → pull → push**（`syncService.sync`）。定时同步调的就是它。
2. **插件没有任何「恢复」动作**。全部动作：提交 / 取消暂存 / 拉取 / 推送 / 同步 / 刷新 /
   查看差异 / 在远端打开 / 停止跟踪 / 放弃合并。没有「放弃更改」「从索引恢复工作区」。
   - 「取消暂存」是 `git restore --staged`（索引退回 HEAD），**工作区一个字节不动** ——
     它丢掉的恰好是「暂存的那份」。
   - 真要恢复得用 `git restore --worktree`（索引→工作区）或
     `git restore --source=HEAD --worktree`（HEAD→工作区），**两个都没暴露**。
3. **暂存的内容扛得住 gc**（合成仓实测）：`git add` 写下的 blob 在
   `git gc --prune=now` 之后**还在**，连 `reflog expire --expire=now --all` + 再 gc 之后
   **也还在**（索引是 git 的可达根之一）。所以「暂存」比工作区安全，但**不如提交**：
   不在历史、不在云端、其他设备看不到，而且一个 `git reset` 或索引损坏就丢掉引用
   → 对象变不可达 → 下次 gc 收走。
4. `intervalMinutes` 默认 10，可设 1..1440。

### 对「拆成短间隔暂存 + 长间隔同步」的判断（未实现，等用户定）

**思路对，但「暂存」是错的机制**，三条理由：

1. **与 pull 冲突（实测两档）**：
   - `pull --rebase`：**一定**被拒 —— `error: cannot pull with rebase: Your index contains
     uncommitted changes. / Please commit or stash them.`
   - `pull`（merge）：改的是**不同文件**时能过（实测 fast-forward 成功）；
     **两边改了同一个文件**时被拒 —— `error: Your local changes to the following files
     would be overwritten by merge: a.md`。
   所以长间隔那一步**在 rebase 策略下必须**先 `commitAll`；merge 策略下多数时候能拖，
   但恰恰在「两边撞上同一个文件」这个最需要它停下的时刻会被拒。方案**没省掉提交，只是推迟**。
2. **风险窗口变长**：现在最多丢 10 分钟的工作，拆完变成 30 分钟。
3. **用户的数据不支持现在就做**：161 提交 / 约 20 个月 ≈ **每月 8 个**，定时器根本没在
   制造提交；而且刚修完的「本地状态文件」已经把最容易制造噪音的那类堵掉了。

### 更好的替代（若真要减提交数）

**合并到上一个尚未推送的提交（amend）**：保持 5 分钟频率，把本次改动并进上一个
**未推送**的同步提交。安全性不降（内容照样进历史），提交数由**推送间隔**决定而不是
定时器间隔。规则要写死：只合并**本插件自动生成的、且 `ahead > 0` 的**那个提交
（别人推过就 `ahead` 归零，自然退化成新提交）。

### 用户的决定：**先不动**

保持现在的定时同步。理由就是上面第 3 条 —— 实际提交率每月 8 个，定时器没在制造提交；
先把「本地状态文件」那一修的效果看一轮再决定。**别在下一轮主动重提这两个方案**，
除非用户先说起，或者出现了新的数据（比如提交数真的开始涨）。

留档的两个未做项（等用户开口）：
- **amend 合并**（上面那段的设计已经完整，可直接照着实现）；
- **「恢复」动作缺口**：插件没有任何「丢弃工作区改动 / 从索引恢复」的动作，
  真要补得单独设计（它是真正的数据丢失动作，要带确认）。

## 轮次：三层保护的分工 —— 实现「检测并提示」+ 定下同步频率

用户要「不脏 git 记录 + 高频防丢失 + 能从旧版本恢复」的方案，然后让我做「检测并提示」，
并问推荐的同步频率。

### 核心结论（这套推理是这一轮最有价值的东西）

**这三件事不冲突，之前觉得冲突是因为把「高频保护」交给 git 了。** git 的恢复粒度是
**全库提交**，而高频恢复要的是**单文件回滚** —— 用提交去满足它，提交数就等于编辑次数。
git 不可替代的价值是**长期 + 跨设备 + 不可变**，那恰恰是**低频**需求。

三层分工：

| 需求 | 粒度 | 谁承担 | 进 git 吗 |
| --- | --- | --- | --- |
| 高频防丢失 | 分钟级、单文件、带 diff | Obsidian「文件恢复」 | **完全不进**（IndexedDB） |
| 云端持久 / 跨设备 | 全库快照 | SyncHub 定时同步 | 进 |
| 从旧版本恢复（>7 天） | 长期、不可变 | git 历史 | 进 |

### 「文件恢复」的实测参数（从 `.probe/app-extract.js` 抠的）

`options = Object.assign({}, {intervalMinutes: 5, keepDays: 7}, await loadData())`；
触发是 `vault.on("modify")` + `workspace.on("file-open")` + 每 60 秒 `resave`；
`defaultOn = true`；存 IndexedDB 的 `backups` 表（按 `path` 索引，带 `ts`）；自带 diff 视图。

**用户两个库里 `file-recovery` 都是 `false`** —— 而且 `sync.enabled` 也都是 `false`。
所以真实风险不是「提交太多」，而是**两层都没兜住**。

### 实现的（很小）

`corePluginState.ts` 的 `corePluginEnabled(json, id)`（纯函数）+ `syncService.fileRecoveryEnabled()`
（只读 `${configDir}/core-plugins.json`）+ `renderSync` 里「注意事项」的**第三条**，
**只在它关着时出现**。设置页预览验过：默认 2 条，`?filerecovery=0` 时 3 条。

三条设计约束：读文件而不是 `app.internalPlugins`（非公开 API）；只读不写（改别人的
核心插件要重启才生效）；**读不出来（`undefined`）时什么都不加** —— 不猜。

### 频率：推荐 30 分钟，并把默认值从 10 改成 30

理由：高频已交给文件恢复 → 定时同步只剩「云端新鲜度 + 跨设备」，而灾难恢复本身要花几小时，
丢 30 分钟与丢 5 分钟没实际差别；跨设备有「立即同步」兜底。间隔越短提交数越线性增长。

**踩到一条测试**：`settings.test.ts` 里那条「不污染 DEFAULT_SETTINGS」的用例把默认值
**写死成 10**（两处）。已改成先捕获 `originalInterval` 再比 —— 断言的是「有没有被污染」，
不该因为「调默认值」而红。**改默认值前先 grep 测试里的硬编码数字。**

### 自我修正：amend 的价值比我上一轮说的小

它当初是作为「短间隔暂存」的替代提的，那条比较仍成立；但 SyncHub 的同步是
commit + push 一体，amend 要有意义得把两者拆开，而拆开之后它提供的「本机高频 git 快照」
和文件恢复高度重叠（后者还更细）。**不是错的，是没必要的。**

## 轮次：去掉面板上的逐文件暂存（发 0.2.2 前）

用户问「你刚才提到暂存会影响拉取，那是不是不应该暂存？」

### 先更正我自己的表述（实测两档，都不准）

| 情况 | `pull --rebase` |
| --- | --- |
| 索引里有暂存 | `cannot pull with rebase: Your index contains uncommitted changes.` |
| **只有工作区改动** | `cannot pull with rebase: You have unstaged changes.` |

**两者都被拒** —— rebase 要的是「索引与工作区都干净」，**不是暂存特有的问题**。
而且 `sync()` 是 commit → pull → push，拉取在提交之后，**正常链路碰不到**。

### 真正的问题（读 `doCommitAll` 才看出来）

`doCommitAll` **无条件 `git add -A`** → **手动暂存了什么对最终提交毫无影响**；
更要紧的是**定时同步到点会把它们一起提交掉** —— 那个按钮**连「暂时不提交」都做不到**。
用户暂存 A 想只提交 A，结果 B 一起进去了。

### 决定：四个按钮 + 两个服务方法一起删（用户选的）

- 删：面板的「暂存此文件 / 取消暂存」+「全部暂存 / 全部取消暂存」、
  `SyncService.stageFiles` / `unstageFiles`、四个 i18n 键。
- **保留**：按暂存状态的**分组**（冲突文件在 `git status` 里同时进 staged 与 unstaged，
  去重后落在「已暂存」那组，所以那组不是空的）；git 层的 `GitManager.stage` / `unstage`
  —— 抽象层词汇，`stage` 还被 `doCommitAll` 用，且 `unstage` 的 `HEAD_UNBORN_RE`
  分支守着「HEAD 未出生时 `git restore --staged` 报 `fatal: could not resolve 'HEAD'`
  （**带单引号**）」这条坑，有集成测试钉着。
- 依据是本仓库已有的同类判断：嵌套仓库行里那个 `minus`（暂存不下）被去掉时的理由 ——
  「**点了没反应的按钮，留着只会让人以为插件坏了**」。暂存按钮更糟：**有反应但没效果**。

**SyncHub 不做选择性提交。** 真要让暂存生效，得同时改「提交」与**自动同步**的行为，
否则自动同步会把这份选择抹掉（那正是这个项目最恨的「以为发生了但没发生」）。

测试改动：删掉 3 条暂存用例 + 1 条整组暂存用例，把「慢提交不插队」那条改用
`untrackPaths`，把「暂存完不会还显示未暂存」改成「动作跑完不会还显示旧状态」。

## 轮次：面板每一行加「放弃更改」（用户要求）

用户原话：「插件侧边栏面板中的更改，应该提供恢复的按钮，等于放弃更改」——
正好补上上一轮那个缺口的反面：面板曾经**只有**「暂存」这类**不生效**的动作，
却**没有**一个「把改动退回去」的**真动作**。

**一个动作覆盖两种场景**（git 眼里是同一件事）：`git restore --source=HEAD --staged --worktree`
- 改坏了想退回 → 被上次提交的版本覆盖；
- **误删了想找回** → 工作区里没有它，于是被**重新写出来**（这是最值钱的那一半）。

**两个 `--` 都要给**：只给 `--worktree` 的话索引里那份还在，`git status` 会显示
「已暂存的更改」—— 用户点的是「放弃更改」，他期待彻底回到原样。

**两类行不给**：
1. **未跟踪的新文件** —— 没有「上次提交」可退（`restore` 会 `pathspec did not match`），
   而「放弃」对它们等于**删掉一个新文件**，丢的东西一点退路都没有；
2. **冲突行** —— 冲突区已有「放弃本次合并」，且面板看不到内容，不该替用户决定用哪一边。

**唯一会丢用户编辑的动作，不可逆** → `ConfirmDiscardChangesModal`：列出**具体哪几个文件**、
把「不可逆」写进正文、确认按钮 `setWarning()`；文案顺带提一句「文件恢复若开着可能还有快照，
但别指望它」（它按 5 分钟节流，不能承诺）。

测试：真仓库 3 条（退回 + **找回误删** + 只动传进来的路径）、服务层 2 条、面板 2 条。
`pnpm check` 八项全过、`pnpm test` **93 文件 1982 用例全绿**、`build:both` 部署两库、
`verify:mobile` 无加载期抛错。

## 轮次：0.2.2 发版完成

用户第二次说「按惯例总结更新发版0.2.2」后完成。

### 过程（含两个新的环境坑）

1. **`github.com` 窗口开了** → 普通 `git push` 一次成功（`3783eec..1f189bb`），
   **不需要** API 重放（`.probe/api-replay.py` 白写了，留着备用）。
2. **推 tag 时又失败**：先是 `CONNECT tunnel failed, response 502`（**代理坏了**），
   去掉代理后变成 `Could not connect ... after 21076 ms`（**github.com 又被阻断**）。
   → 改用 **API 建标签**：`gh api repos/.../git/refs --method POST -f ref=refs/tags/0.2.2 -f sha=<HEAD>`。
   标签是**轻量标签**（与历史一致，`git cat-file -t` 显示 `commit`）。
3. **GitHub release 正文 = CHANGELOG 里该版本的段落**（读 0.2.1 的 body 确认的，
   与 RELEASE.md 说的「手写精简版」不同 —— **以实际为准**）。用 Python 从 CHANGELOG
   抽出 `^## \[0\.2\.2\].*?(?=^## \[)` 写成 `.probe/release-0.2.2.json`，
   再 `gh api --input` 提交。
4. 资产用 `gh release upload 0.2.2 main.js manifest.json styles.css --clobber`，
   读回 `digest` 与本地 sha256 **逐字节一致**。
5. **Gitee 的 tag 没有自动同步**（只同步了 `refs/heads/main`）→ 手动推：
   `git -c credential.helper= -c 'credential.helper=!f(){ echo username=oauth2; echo password="$GITEE_TOKEN"; }; f' push --no-verify gitee 0.2.2`
   （**用户名是 `oauth2`**，不是账号名）。
6. `GITEE_TOKEN=... pnpm gitee:release 0.2.2` → 3 个附件、字节数吻合；
   再**下载回来比对 sha256**，三个全一致。

### 新的环境坑（值得记）

**`sha256sum` 在 Git Bash 下对含反斜杠的路径会给整行加一个前导 `\`** ——
`awk '{print $1}'` 取到的第一个字段是 `\4538e354…`（反斜杠和哈希粘在一起），
`cut -c1-16` 于是截成 15 位，**看起来像「不一致」**。要 `| tr -d '\\'` 去掉。
（`$TEMP` 是 `C:\Users\...\Temp`，所以下载到那里必然触发。）
**校验下载件时先确认这个转义**，否则会误判成「资产传坏了」。

- Gitee：`refs/heads/main` 自动同步到 `1f189bb`，tag 手动推过去；release + 3 附件，
  下载回来 sha256 全一致。
- 本地：工作区干净，`manifest.json` 版本留在 `0.2.2`。
