## 轮次：重排插件安装器页 + 自身更新接入自动检查与标签徽标

用户原话：「调整插件安装器的卡片顺序，将当前版本0.1.9·尚未检查更新的小字提示放到
最前面，然后展示SyncHub自身更新卡片，然后是启用gitee镜像源更新SyncHub设置项，
再然后是进入设置页时自动检查设置项，且打开该设置项时，进入设置页检查更新的同时也
检查SyncHub自身，并在插件安装器标签页也提供数字标识提示，最后展示启动时检查更新、
启动检查延迟、自动发现gitee镜像设置项。」

### 改了什么

- **页内顺序**（`renderInstaller`）：页面标题 → 状态小字 → 自身更新卡片 →
  镜像源开关 → 进入设置页时自动检查 → 启动时检查更新 → 启动检查延迟 → 镜像发现。
  `renderSelfUpdate()` 拆成三段：状态行（**先于卡片创建**，DOM 顺序即创建顺序）、
  卡片、来源开关。页面标题保留在最前（那是页签本身的标题）。
- **新增设置字段 `installer.selfUpdateAvailable: string`**（空串 = 没有），
  **不需要版本号迁移**（纯新增字段，`mergeWithDefaults` 补默认值）。
  理由写在字段注释里：标签栏在页面内容**之前**画、重启后也要还在 ——
  与 `availableUpdates` 同一条（只放内存徽标会永远慢一拍）。
- `UpdateChecker.checkSelf` 内部调 `InstallerService.recordSelfUpdateCheck` 落盘
  （与 `checkAll` → `recordUpdateChecks` 同一个形状）。**放在 checkSelf 里而不是
  调用方**：两个入口（手动按钮 + 自动检查）都要写同一份记录，各写一遍迟早漏一个。
  它顺带刷 `lastUpdateCheckAt` —— 这一条比 `recordUpdateChecks` 那边更要紧：
  那边只在 `results.length > 0` 时写，而**一个跟踪项都没有的用户走不到那条路**，
  不在这里写的话他每次打开设置页都会重打一遍 Gitee 接口。
- `updateSelf` 成功后清掉 `selfUpdateAvailable`（否则标签徽标一直亮着）。
- **`shouldCheckOnSettingsOpen` 去掉 `trackedCount` 入参**：这一条判据现在同时管
  「查跟踪列表」与「查 SyncHub 自身」，而后者跟跟踪列表无关 —— 一个插件都没跟踪的
  用户同样该知道自己有没有新版本。「有没有跟踪项」交给调用方在跟踪那一轮自己判。
- `autoCheckOnOpen` 改成两件事一起做，收尾**统一重绘一次**（`checkAllUpdates` 加
  `redraw` 选项，自动检查那条路传 `false`，避免刚打开的页面被连着重画两遍）。
- `renderInstallerBadge`：SyncHub 自身有可用更新时，在「插件安装器」标签上挂
  `1`（`obsync-tab-count is-update`，与「已追踪插件」那套样式一致）。
  只写 `1`：这一页要处理的事只有自身更新这一件，版本号放不下、也不该放。
- 状态小字用**落盘结果**兜底（`knownCheck()`）：否则会出现「状态说尚未检查、
  徽标却亮着」的自相矛盾。

## 轮次：「初始化 git 仓库」的状态徽标（用户报的两个毛病）

## 轮次：讨论「图片同步改成即时同步」（只是问，还没动手）

用户问：「其实图片同步如果不做按周期同步，做即时同步会更好吧？变动即时同步应该不影响
软件性能吧？」——查了一圈代码，结论与依据记在这里（下次要动手时不用再查一遍）：

- **一轮同步的成本很小**：`scanLocalImages` 走的是 Obsidian 的内存文件索引
  （`vault.getFiles()` + `stat.size/mtime`），**不读盘、不算哈希**；`decide()` 只比
  `size / mtime / etag`。网络侧是 `listAll()`（每 1000 个对象一页，通常 1 次请求）
  + 真正要传的字节。所以「跑一轮」≈ 一次 R2 往返 + 几毫秒 CPU，真正的开销是传输本身。
- **即时同步的零件其实已经在了**：`syncPath()`（图片编辑器保存后就在调）、
  `syncSelection(paths)`、`renameRemoteBackup()`（`vault.on("rename")` 已经在即时搬
  云端）、`noteDeleted()`（删除事件驱动）。缺的只是把 `create` / `modify` 接上。
- **⚠ `syncPath()` 是无条件上传**（不查远端、不按 `conflictPolicy` 判）—— 它适合
  「刚保存完的这一份」，**不适合当通用钩子**（会绕过冲突策略、盖掉别处的新版本）。
  通用钩子该用 `syncSelection([path])`：跑一遍完整计划再只执行那几个路径的动作
  （多一次 ListObjects，但判据与面板一致、有单测覆盖）。
- **接事件要处理四件事**：① 下载走 `vault.createBinary/modifyBinary`，会触发
  `create`/`modify` → 自触发循环，必须标记自己写的动作（`panelDeleted` 是这个形状的
  先例）；② 大文件分块写时 `modify` 会提前触发 → debounce 是必需而非优化；
  ③ `run`/`syncSelection` 在跑时会抛 `already running`，而现在
  `ImageAutomatics.fire()` 的处置是「放弃这一轮、等下一个整周期」—— 即时同步没有
  「下一个周期」可等，要记 pending 补一次；④ 过滤用 `TFile` → `isImagePath` →
  `isInsideFolders`，与 `noteDeleted`/`noteRenamed` 同一套。
- **不能拿即时替掉周期**：即时只看得见**本机**的变动；另一台设备传的图、或桶里手工
  删掉的对象，本地没有任何事件，永远不会被拉回来。所以周期同步要留着当兜底
  （可以把默认周期拉长）。另外移动端「掉进库就立刻传」= 蜂窝网络下立刻上传几 MB，
  值得单独想（移动端仍走周期，或加「仅 Wi-Fi」）。
- 现状供参考：`autoSyncEnabled` 默认 **false**、周期默认 10 分钟；`run()` 的四个调用
  点是「周期到点 / 启动一轮 / 命令面板 / 设置页那个立即同步按钮」。

### 用户的反提：改成「变动后静默 30 秒再同步」

用户问：「那如果换个思路，变动延时同步呢？比如图片增、删、改、重命名等变动之后30s后
无额外变动，则自动同步，是不是就比推荐的即时同步+周期同步要好？」

结论：**这条路更好，但它替代的是「即时」那半边，不是「周期」那半边。**

- 它解决不了「别处变化」：另一台设备传的图 / 桶里手工删的对象，本机**没有事件**，
  计时器永远不会被启动 → 仍然要留一个周期当兜底（职责变成「拉回远端漂移」，
  所以可以拉长到 30–60 分钟）。
- 它比我原来建议的「即时 3s + 周期 10min」更干净：触发器从两个变成一个语义
  （「你停手半分钟后我就同步」），而且天然避免「周期到点正好插进用户编辑中间」。
- 三个必须加的细节：
  1. **maxWait**（比如 5 分钟）：一直在动时静默期永远不满足 → 永远不跑，必须兜住。
  2. **编辑器保存那条路保留立即 `syncPath()`**：那是「我改完立刻要结果」的场景，
     30 秒会显得钝；别让延时机制把它接管。
  3. **关窗丢窗口**：在 30 秒静默期内关掉 Obsidian，这次改动要等下次启动那一轮
     （`start()` 里那一轮本来就有）—— 可接受，但要知道。
- 延时**不改变**「跑一轮」的成本（一次 ListObjects + 传输），改的只是**触发时机**。
- 移动端流量那条考虑与选哪个方案无关（该传的还是会传，只是晚 30 秒）。

### 用户让我出方案 → 写了 `docs/image-sync-design.md`

用户说「你能否帮我设计一份比较合理的图片同步方案，我说的或许不是最合适的」。
方案落在 `docs/image-sync-design.md`（**提案，代码还没按它改**）。要点：

- 立足点是「**谁看得见哪种变化**」：本机→云端（事件看得见）、云端→本机（**事件看不见**）、
  用户的显式意图（要立刻响应）。任何「只靠事件」的方案都会漏掉中间那条 ——
  这是「不能拿即时同步替掉周期同步」的根本原因。
- 四个触发器分工：变动后静默同步（新，默认开，静默 30s / maxWait
  `clamp(静默期×10, 5min, 30min)`）、周期同步（改职责为「拉回别处的变化」，默认周期
  建议 10→30 分钟）、编辑器保存立刻 `syncPath`（保留）、启动一轮（保留）。
- **删除不触发变动同步**（它已有即时处置，而同步从不删云端；触发它唯一可能的效果是
  把云端那份拉回来）。**编辑器保存不抑制**（重叠一次 LIST 换「syncPath 失败后自愈」）。
- 明确不做：单路径快路（一次 LIST 覆盖任意改动数，且不另起一套判据）、更勤的远端轮询、
  按网络类型区分（Obsidian 没有可靠的网络类型 API）。
- 默认开「变动后自动同步」的理由：它与「每隔 N 分钟无条件跑一轮」不同，只在**用户真的
  动了图**之后跑，与 `images.enabled` 默认 true 同一条论证。
- 落地分五步，第一步是抽 `ImageChangeQueue` 纯逻辑 + 单测。

### 落地时才发现的三个细节（都写进代码注释与设计文档第十节了）

1. **`selfWrites` 不能是裸 `Set`**：标记靠**事件**消费，而**写失败时不会有事件**
   （`writeLocal` 直接抛错）→ 残留标记会把用户**后来**对同一个文件的真实改动吃掉。
   改成 `Map<路径, 标记时刻>` + 10 秒 TTL。
2. **`noteRenamed` 也要入队**：`renameRemoteBackup` 成功时那一轮是白跑，
   但它**失败**时靠这一轮把新路径补传上去。
3. **队列里「正在跑」那条路不能走 `arm()`**：`arm()` 会把 `untilMaxWait` 算成 0，
   变成「立刻重试」的死循环 —— 直接 `setTimeout(BUSY_RETRY_MS)`。
