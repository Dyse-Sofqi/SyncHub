# 图片同步：触发器设计（2026-10-06）

> 起因：用户问「图片同步如果不做按周期同步，做即时同步会更好吧？」，随后自己改口提出
> 「变动之后 30s 内无额外变动再同步」。**后者是对的**，但它只覆盖了一个方向 ——
> 这份文档把「什么时候同步」按**谁看得见哪种变化**拆开，每个触发器只管它能看见的那类。
>
> **状态：已按本文实现**（2026-10-06 当天落地）。实现与本文的差异记在第十节，
> 落地顺序见第九节（每步都已验收）。

---

## 一、先划清三个方向

| 方向 | 例子 | 能被本地事件看见吗 |
| --- | --- | --- |
| **A. 本机 → 云端** | 用户拖进一张图、用编辑器裁剪、批量重命名 | ✅ 会 |
| **B. 云端 → 本机** | 另一台设备传的图；用户在 R2 控制台手工删了一个对象 | ❌ **不会**（本机什么都没发生） |
| **C. 用户的显式意图** | 「保存这张」（要立刻有结果）、「删掉云端那份」 | ✅（且必须立刻响应） |

**整份设计的立足点就是这张表。** 任何「只靠事件」的方案都会漏掉 B —— 这也是为什么
「把周期同步整个换成即时同步」不成立。B 只能靠**主动去问**（定时轮询）。

## 二、当前实现（起点）

| 触发器 | 覆盖方向 | 状态 |
| --- | --- | --- |
| 启动后跑一轮（`ImageSyncModule.start()`） | A + B | 已有 |
| 手动：命令面板 / 设置页「立即同步」/ 面板「同步选中」 | A + B | 已有 |
| 周期（`images.autoSyncEnabled`，**默认关**，周期默认 10 分钟） | A + B | 已有 |
| 编辑器保存 → `service.syncPath(path)` | A（单张，立刻） | 已有 |
| 库里改名 → `service.renameRemoteBackup(from, to)`（服务端 COPY） | A（立刻） | 已有 |
| 库里删除 → `noteDeleted()`（攒批 400ms → 问一句 → 记墓碑） | C | 已有 |

**缺口只有一个**：用户在库里**直接**动图（拖进来、外部程序替换、Obsidian 之外编辑），
云端要等到「下一轮周期（默认根本没开）」或者「重启后的启动那一轮」才更新。
这次要补的就是它。

## 三、成本模型（决定「能跑多勤」）

| 环节 | 开销 |
| --- | --- |
| 扫本地 `scanLocalImages` | 走 Obsidian 的**内存文件索引**（`vault.getFiles()` + `stat.size/mtime`），**不读盘、不算哈希** → 毫秒级 |
| 判断 `decide()` | 只比 `size / mtime / etag`，纯内存 |
| 列云端 `listAll()` | **每 1000 个对象 1 次请求**，通常就是 1 次 R2 往返 |
| 传输 | **真正的成本**（该传的字节） |

**推论（后面几个决定都从这三条来）**：

1. **一轮的固定成本 ≈ 1 次 R2 往返。** 所以「跑得勤」不贵，「传得勤」才贵。
2. 攒批的收益是**减少往返次数**，不是减少传输量 —— 该传的图一张都省不掉。
   所以「静默期多长」主要不是成本问题，而是**延迟 vs 抖动**的取舍。
3. **不要为「只改了一张图」另写单路径快路。** 一次 LIST 覆盖任意数量的改动，
   而 N 个路径逐个 `HeadObject` 是 N 次往返；更要紧的是那样会**另起一套「谁该传」的
   判断**，绕过已经穷尽单测的 `decide()`（`syncSelection` 的注释里已经为面板写过
   同一条理由）。桶里对象上万、LIST 要翻很多页时才值得重新考虑。

## 四、提案：四个触发器，各管一件事

| 触发器 | 管什么 | 默认 | 为什么是它 |
| --- | --- | --- | --- |
| **变动后静默同步**（新） | A | **开**，静默 30s | 主力：本机改动最常见的路径 |
| **周期同步**（改职责） | B | 沿用（默认关），周期建议 30min | **唯一**能看见别处变化的 |
| **编辑器保存**（保留） | C | 始终 | 用户刚改完，要立刻有结果 |
| **启动一轮**（保留） | 兜住「静默期内关窗」 | 始终 | 已经在了 |

### 4.1 变动后静默同步（新增）

```
vault.on("create" | "modify" | "rename")
  → file instanceof TFile
  → isImagePath(file.path)
  → isInsideFolders(file.path, normalizeFolders(settings.folders))
  → 入队 + 重置静默计时器
        ↓  静默 30 秒（期间没有新变动）
   service.syncSelection(队列)
```

- **静默期 30 秒**：一次编辑会话（拖 50 张图、批量压缩一批、连续改名）被收成**一轮**；
  而且**不会在用户还在动的时候开跑** —— 这一条比「省请求」重要得多：有些程序分块写
  大文件，`modify` 会在写到一半时触发，那时去读会上传一个截断的图。
- **硬上限 maxWait**：`clamp(静默期 × 10, 5 分钟, 30 分钟)`（默认 30s → 5 分钟）。
  没有它就有死角：用户连续动几百张图时静默期永远不满足 → **永远不跑**。
- **与正在跑的一轮撞上**：记 `pending`，那一轮跑完**立刻补一次**。
  不能沿用 `ImageAutomatics.fire()` 那句「放弃这一轮、等下一个整周期」——
  变动同步没有「下一个周期」可等，丢掉就是**永久丢失**（要等下次启动）。
- **自触发抑制**：下载走 `vault.createBinary` / `modifyBinary`，那**会触发**
  `create` / `modify` 事件 → 「下载 → 触发同步 → 又下载」的循环。用一个短窗口的
  `selfWrites` 集合标记插件自己写的那几个路径（`panelDeleted` 是这个形状的先例：
  **自己做的动作要标记，否则会被自己再处理一遍**）。
- **总开关关掉时不监听**：`images.enabled` 为假 → 一个监听都不挂（与 `noteDeleted`
  同一套边界：那是用户明确说了「别在背后动我的图片」）。

### 4.2 周期同步：保留，但**改职责**

- **不能删。** 删了就等于「B 方向只在换设备/重启时才生效」。
- 职责从「同步本机改动」变成「**拉回别处的变化**」，所以周期可以从 10 分钟拉长到
  **30 分钟**（只影响新用户的默认值；老用户的 `data.json` 里存着 10，不动它）。
- 设置页那一行的描述必须跟着改 —— 否则用户会以为它在干变动同步那份活。

### 4.3 编辑器保存：保留立即上行，且**不抑制**

编辑器保存后立刻 `syncPath()`（已有），同时那次写入也会触发 `modify` →
30 秒后又跑一轮，而 `decide()` 会把那一张判成 `in-sync` 跳过。

**故意不把编辑器写入加进 `selfWrites`**：重叠一次的代价只是 1 次 ListObjects，
换来的是「`syncPath` 失败（云端不可达、令牌过期）时 30 秒后自愈」。
把它抑制掉，那条失败路径就只剩「等下一轮周期」——而周期默认是关的。

### 4.4 删除：**不**触发变动同步

- 删除已经有自己的即时处置（问一句 + 记墓碑），而同步**从不删除云端**。
- 所以「删完再跑一轮」唯一可能的效果是**把云端那份拉回来**
  （`deleteRemotePolicy: "never"` 那一档的既定行为，设置页描述里写明了）。
  那不是「刚删完一张图」该看到的反馈。
- 它仍会被周期那一轮照旧处理 —— 行为与现在完全一致，这次不改。

## 五、明确不做的事

| 不做 | 为什么 |
| --- | --- |
| **只靠事件、去掉周期** | B 方向没有事件（见第一节）。这是本方案与「纯即时同步」的分界。 |
| **单路径快路**（只改一张时走 `HeadObject`） | 见第三节推论 3：一次 LIST 更划算，且不另起一套判据。 |
| **比周期更勤的「远端轮询」** | R2 LIST 再便宜也是网络请求；而远端变化的时效要求低 —— 它不是用户当下在等的东西。 |
| **按网络类型区分（仅 Wi-Fi）** | Obsidian 没有可靠的网络类型 API（`Platform` 只给 `isMobile` / `isDesktopApp`）。所以移动端只能让用户自己关那个开关，代价写进描述。 |
| **碰删除的语义** | 「`run()` 只复制、从不删除」是这个模块的底线（2026-09-23 的结论）。任何新触发器都不改变它。 |
| **绕过 `conflictPolicy`** | 所有自动路径都走 `decide()`。特别地：**不要拿 `syncPath()` 当通用钩子** —— 它是无条件上传（不查远端），只在「用户刚保存完这一份」时才成立。 |

## 六、设置页怎么变

新增一行（排在「自动同步图片」之后、「按周期同步」之前）：

| 行 | 控件 | 默认 |
| --- | --- | --- |
| **变动后自动同步** | 开关 + 延时（秒，5–600） | 开 / 30 |

「按周期同步」那一行：

- 描述改成「按周期去云端**核对一次**，把其他设备上的改动拉回来（本机的改动由上面那一项负责）」；
- 默认周期 10 → 30 分钟。

「注意事项」那一块补一条：**手机上开着变动同步，会在蜂窝网络下立刻上传**
（这是用户自己掏的流量，必须说出来）。

## 七、默认值：为什么「变动后自动同步」可以默认开

「按周期同步」默认关的理由是「图片同步会真的读写文件与网络，不该在用户没要求时自己跑起来」。
新增这一项默认开**不违背**那条，区别是具体的：

- 周期同步 = 「**每隔 N 分钟无条件跑一轮**」，用户没动任何东西它也会跑；
- 变动同步 = 「**你真的动了图之后跑一次**」，代价与收益一一对应。

而且 `images.enabled` 默认就是 `true`，它的注释写着：「没配好之前它什么也不做，
而配好之后还要求用户再找一个开关才生效，是多余的一步」——
用户配好 R2 的意图本来就是「把图同步上去」。同一条论证在这里成立。

## 八、要写测试的地方

攒批/静默/上限/pending 这一段**抽成纯逻辑**（照 `shouldCheckOnSettingsOpen` 的做法：
纯函数 + 单测，`vault.on` 的接线留给探针/真机），需要覆盖：

1. 一次变动 → 静默期满才跑；期间再来变动 → 重置；
2. 连续变动不停 → **maxWait 到点仍然跑**（这一条最容易漏）；
3. 一轮在跑时来的变动 → 跑完**补一次**（不丢）；
4. 插件自己下载写盘 → **不**重置计时器（自触发抑制）；
5. 受管范围之外的图片、非图片文件 → 不重置；
6. 删除 → 不重置；
7. `images.enabled` 关着 → 一个监听都不挂。

## 十、实现与本文的差异（都是落地时才发现的具体问题）

1. **自触发抑制用的是「路径 → 标记时刻」的 `Map` + 10 秒 TTL，而不是裸 `Set`。**
   本文写的是「一个短窗口的 `selfWrites` 集合」。落地时发现裸 `Set` 有个漏洞：
   标记靠**事件**来消费，而**写失败时不会有事件**（`writeLocal` 直接抛错）——
   那个标记会一直留着，把用户**后来**对同一个文件的真实改动吃掉。
   存时刻之后，那种残留自己就过期了（`SELF_WRITE_TTL_MS`）。
2. **`noteRenamed` 也会入队。** 本文只说了 `create` / `modify` / `rename` 都要挂，
   但没说改名之后要不要触发一轮：`renameRemoteBackup` 用服务端 COPY 搬云端那一份，
   成功时新路径已经是 in-sync（跑一轮会白跑）。仍然入队，是因为**它可能失败**
   （云端 COPY 不通）—— 那时这一轮会把新路径当「本地有、云端没有」补传上去。
   一次多余的 `ListObjects` 换「改名失败能自愈」，值得。
3. **删除**（`delete`）**完全不参与**，与本文一致，但落地时把理由写进了代码：
   同步从不删云端，所以触发一轮唯一可能的效果是把云端那份**拉回来**
   （`deleteRemotePolicy: "never"` 那一档），那不是「刚删完」该看到的反馈。
4. **编辑器保存那条路仍然不抑制**（本文的决定），于是保存之后会有一轮「白跑」
   （`decide()` 判成 in-sync）—— 换来的是 `syncPath` 失败时 30 秒后自愈。
5. 设置项的实际命名：`imageChangeSyncEnabled`（默认开）、`imageChangeDelaySeconds`
   （默认 30，范围 5–600）。周期默认值由 10 分钟改成 **30** 分钟（只影响新用户）。
